# Activation passphrase (PlanCope Local Host)

## What it is

The activation passphrase is the single bootstrap secret that ties a PlanCope
Local Host machine to the encrypted padrón. It implements **decision 4**
(`docs/plan-cicd-batches.md`, "Decisiones tomadas"): activation-once-per-machine
via passphrase + Windows DPAPI. On each machine the operator enters the
passphrase exactly once; the resulting local secret is protected with DPAPI
(`DataProtectionScope.CurrentUser`) and stored locally, and from then on only
the CUE is typed at activation time — never the passphrase again.

## Why it exists

Because of **decision 5**: the CUE can never be the key. CUEs are sequential and
public (`180000100`, `180000200`, `180000300`, …); they identify educational
establishments, not people. If the CUE derived or unlocked the decryption key,
an actor holding the public binary could iterate the 1,440 known values and
dump the 227,598 student records without any other credential. The key must
depend on a secret that is neither in the binary nor derivable from public
data — the activation passphrase.

## Initial emission per release

The passphrase is generated by the person preparing the release, on the same
machine that is the only place where the real dataset is handled
(`docs/plan-cicd-batches.md`, section 3 — "el dataset real sólo se manipula en
la máquina de quien prepara el release"). There is no automated generator in the
pipeline, and no task in this repository emits one.

Handling rules for the passphrase, per section 3 ("qué nunca debe llegar a un
artifact público"):

- It is **never committed** to the repository.
- It is **never logged** — not in a GitHub Actions log, not in an artifact, not
  in a release body or a release metadata asset, not in an application log.
- It is **never sent through GitHub Actions or Coolify** — not as an
  environment variable, not in a deploy payload, not in any service
  configuration.
- It is delivered to field operators **out-of-band**, the same way for the
  initial emission and for any later one.

## Rotation policy

**Closed decision** (see `docs/plan-cicd-batches.md`, section 9, open question
#4 — RESOLVED): the passphrase is rotated **only when its compromise is
suspected**. It is never rotated on a fixed release cadence and never rotated
automatically.

### Who triggers a rotation

The person responsible for release preparation, on suspicion or a confirmed
report of compromise. There is no automated trigger; no workflow or schedule
rotates the passphrase.

### How the new passphrase is redistributed

Out-of-band, with exactly the same handling rule as the original emission: it is
never sent through GitHub Actions logs, Coolify, or any committed artifact.
Field operators receive the new passphrase by the same out-of-band channel used
for the original one.

### What happens to machines already activated with the old passphrase

They keep working locally. Activation establishes a DPAPI-protected local secret
per machine (decision 4), and rotating the passphrase does **not**
retroactively invalidate that already-established local secret. Already
activated machines are unaffected until their next required re-activation; the
rotation only affects future **first-time** activations. A machine that must
re-activate before receiving the new passphrase stays usable with the key it
already has.

### Rationale

With 1,440 CUEs / school machines, rotating on every release would force
re-activating the whole fleet of machines; the operational cost is not justified
against the risk. Hence: rotate **on suspected compromise only**.
